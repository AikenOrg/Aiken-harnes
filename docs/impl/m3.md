## スキーマ

`docs/spec/10-storage.md` の 3 節を参照。`schema_version = 1`。

- `sessions` / `messages` / `job_results`
- `messages` は `(session_id, seq)` 主キー、`interrupted` を保持
- `job_results` は結果本体と通知状態を保持
- `session.deleted` でカスケード削除

## 復元

```text
session.restore(id)
  -> session-store.load
  -> core: restoring
  -> history-store.loadMessages -> ctx.history.restore
  -> result-store.listBySession
       running -> failed (interrupted)
       terminal & !notified -> 通知キュー
  -> idle + session.restored
```

- `restore: "last"` は起動時に `latestRestorable()` を 1 件だけ復元する。
- ループは再開しない。
- 復元失敗は `error` 状態。再試行時に error セッションとメモリ履歴を破棄する。
- 保存モデルのプロバイダーが現 config に無い場合も `error` にしてモデル ID を返す。
- 強制終了で `tool_call` だけが残った場合、`interrupted by restart` の `tool_result` を補う。
- `tool.completed` / `turn.ended` で flush し、損失範囲を小さくする。
- result-store が無い場合、ジョブ・結果・通知状態は復元されない。

## TTL / 削除

- 起動時 + 既定 6 時間ごとに `deleteExpired(30)`。
- 対象は終端かつ通知済みのみ。running / 未通知は残す。
- `session.delete` は closed のみ。DB は `session.deleted` でカスケード削除。

## 制限

- メッセージ追記は 50ms / 100 件でバッチ化。他の書き込みの前後で順序を保つ。
- Windows 実機の DB パス確認は未実施。
- ログ全文検索 (FTS)、approvals、compaction はスコープ外。
- result-store なしの構成では通知状態を復元できない（仕様どおり）。
